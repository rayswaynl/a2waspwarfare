### Open contradictions in the engine-truth model (do not paper over these)

1. **The "connect-timing governs honoring" theory is a repeated correlation, not a proven mechanism, and even the repo's own best evidence for it is not a clean binary.** `Init_CommonConstants.sqf:3522`'s dated comment, read in full this session, actually cites **two different measurements** in the same paragraph: (a) a registration-timing pair from the lobby-lock's own clock ("HC-AI-Control-1 registered at mission time ~3s and HC-AI-Control-2 at ~57s" — used to justify the 90→150 raise), and (b) a **separate** connect-timing claim used to justify the 150→240 raise: "HC1 still takes a WEST player slot because it connects while the mission is still loading... vs HC2 **which connects ~10s *before* mission-live** and gets CIV." Read literally, HC2 got CIV while connecting *before* `MATCH|v1|START`, not after — which undercuts a strict "honored only once truly live" binary and suggests the real boundary (if there is one at all) is fuzzier, or gated on something other than the `MATCH` marker specifically. No document in this repo identifies what that boundary actually is.
2. **A directly-dated, earlier (archived) investigation reached the opposite conclusion.** `docs/design/archive/HC-SLOT-MAGNET-HANDOFF.md` (June 2026) concluded: "Delay the HC launch (JIP): no effect... The engine seats lowest-WEST whenever the HC connects... regardless of timing." No document in this repo reconciles the two positions, and the underlying live tests behind each are not re-verifiable from source.
3. **Clock-scale ambiguity.** The 2026-08-05 fresh evidence's "ticktime" values (`HCLOBBY ARMED@222`, `HC1 connect@230`) are most consistent with `diag_tickTime`/process-uptime (`Init_HcLobbyLock.sqf` is `execVM`'d immediately after the HC registry is created, well before the `commonInitComplete && townInit` gate and well before `MATCH|v1|START`). The changelog's "~3s/~57s" and "~540-566s" figures are on a **different clock** (mission `time`, and wall-clock-from-restart-script-kickoff, respectively). These three numbers should never be compared directly without a single boot that logs all three together — which was not done for the 2026-08-05 boot. **This is the single most valuable missing data point** (see §8).
4. **Whether the box's real launcher script was ever actually patched for the documented 420s-vs-566s mismatch is unknown.** No changelog after `m0730h` (2026-07-30) claims it was fixed, and the script itself does not exist in this or any known worktree — so the fresh 2026-08-05 evidence is fully consistent with the bug simply never having been fixed, six days later.

## 4. Chosen design + mechanism

**Verdict: synthesis of the three candidates, not a single one adopted wholesale.** Two phases:

- **Phase 1 (box-side, the actual fix):** a theory-agnostic **verify-then-bounce** step, adapted from `wasp-hc-seat-fix-design`. It does not need the connect-timing theory to be exactly right (see open contradiction #1 above) — it measures the one ground-truth signal that exists (`HCSIDE|v1|preseat|engineSide=`) per HC and, if wrong, performs the one action every source agrees has repeatedly worked (kill + relaunch that one HC once the mission is already live), bounded and idempotent. This is the only lever capable of actually freeing an engine-level slot binding — mission SQF categorically cannot (§2, items 1–2).
- **Phase 2 (mission-side, defense-in-depth):** the small, low-risk, already-established-idiom consumer hardening independently verified in this session (`Server_VoteForCommander.sqf`, `server_victory_threeway.sqf` x2, the `Init_HcLobbyLock.sqf` Caster-slot landmine, the `WFBE_C_HC_CIV_RESLOT` comment). This closes the residual blast radius during the (now-bounded, and shrinking) window before Phase 1's bounce converges, and costs almost nothing to ship.

### Mechanism detail — Phase 1: Confirm-HCSeatOrBounce

1. **Prerequisite (cheap, do first, on whichever script is actually live — see Open Owner Decision #2):** raise the real launcher's `MATCH|v1|START` wait ceiling past this hardware's measured cold-load time. `Start-Wasp-4HC.ps1:28`'s own default (420s) is the exact value `CHANGELOG-m0730h` proved insufficient for this hardware (measured ~540-566s) — reuse `Start-Wasp-4HC.ps1`'s already-working wait/offset/fallback pattern verbatim rather than inventing new logic, with the ceiling raised to (say) 700s.
2. This alone is **not** sufficient — it reduces how often a bounce is needed, it does not replace the need for one, because the connect-timing theory it rests on is explicitly not proven (§2 contradiction #1) and an earlier archived test concluded the opposite (§2 contradiction #2). Verification must still happen.
3. After the (unmodified) HC-launch loop and settle, record a fresh RPT byte offset (same offset-tracked pattern already proven in `Start-Wasp-4HC.ps1:49-56`, so a stale prior-boot marker can never false-positive).
4. Per expected HC name (`HC-AI-Control-1`, `HC-AI-Control-2`, from `WFBE_C_HC_NAMES`), poll the RPT tail (shared `ReadWrite` open, never locks out the live server writer — same idiom as `Start-Wasp-4HC.ps1:67`) for that HC's `HCSIDE|v1|preseat|name=<X>|engineSide=<Y>` line, bounded ~90s.
5. **Ground truth check, never trust the post-reseat line:**
   - `Y == 'CIV'` → PASS, done for this HC.
   - `Y` is `GUER`/`RESISTANCE`, or anything not `CIV`/`WEST`/`EAST` → **immediate CRITICAL alert, no automatic retry.** The owner's explicit "GUER volume is the point" concern means an HC that ever lands on a GUER slot must never be auto-retried blind; a human looks at it first.
   - `Y` is `WEST`/`EAST` (the observed case) or no preseat line appears within the poll window (fail-closed, never "assume fine") → bounce:
     a. Identify the specific OS process for that HC via the **exact, already-proven** filter (`Get-CimInstance Win32_Process -Filter "Name='ArmA2OA.exe'"` + `CommandLine` containing the `-name=HC-AI-Control-<n>` token, quotes stripped) — the identical pattern `hc_launch.cmd` and `Verify-4HC.ps1` already use. This guarantees the kill targets only that one HC process, never the server, never the other HC, never a human.
     b. `Stop-Process` that PID only. **Verified caveat:** `hc2_launch.cmd` has no self-kill guard of its own (item 13, §2) — the bounce script must do this kill itself before relaunching HC2; do not add a blind image-wide `taskkill` (that would kill HC1 too).
     c. Relaunch via the same unmodified per-HC `.cmd` file. Because step 1's wait has already completed, this reconnect is a JIP into an already-live mission — the one condition every source (`Init_HcLobbyLock.sqf:6`, both changelogs, the owner's own "WaspBounce2 empirically re-seats HCs to CIV" observation) agrees has worked.
     d. Re-run CPU affinity for the new PID (`Set-WaspAffinity.ps1` / `Verify-4HC.ps1`'s own recompute logic) — the old PID's pinning is now stale; skipping this silently degrades HC performance on every bounce.
     e. Settle, re-poll for a **new** preseat line at the new RPT offset.
   - Bounded: max 2 bounces per HC (3 total connect attempts), increasing settle (20s/40s), then **stop** — log CRITICAL and hand to the existing DM/alert path rather than looping or silently declaring success.
6. Idempotent per boot (marker keyed to the pre-launch RPT offset).
7. **Hard scope fence:** runs only once, at boot/restart, immediately after HC launch — **never** wired into any periodic/mid-round health check. Rationale: HC hosting is creation-based (§2 item 1); killing an HC after it has delegated real town-AI/commander-team groups would orphan them. Running only at boot, before delegation is meaningful, keeps this risk near zero.
8. Ships behind an explicit default-OFF switch. The existing chain is untouched until the switch is passed explicitly and proven (§6).

### Mechanism detail — Phase 2: consumer hardening

Apply the exact, already-established `!((name _x) in WFBE_C_HC_NAMES)` idiom (verified live today in `Common_CreditSidePlayers.sqf:29`) to the two confirmed-unpatched consumers, plus defuse two dormant, currently-inert landmines. All four are narrow, single-purpose diffs; none touch HC architecture, JIP flow, or slot allocation.

## 7. Test plan (cold-start proof)

Must be proven on a genuine **cold boot** — full stop of the dedicated server and both HC processes, RPT left un-rotated so offset-tracking is genuinely exercised. A warm restart or JIP-only test proves nothing: `Init_HC.sqf`'s own persistent 15s reseat watcher already self-heals a same-process MISSINIT restart, and the failure in question is specifically a cold-boot phenomenon.

1. **Negative control (do this first, before touching anything):** cold-boot with the **current, unpatched** chain. Confirm the known failure signature reproduces — an `HCSIDE|v1|preseat|...|engineSide=` line that is not `CIV` for at least one HC, **and** a role-select screenshot showing that HC in a faction-colored (not CIV) row. If it doesn't reproduce this run, re-run before drawing any conclusion later — a passing "after" run means nothing if the "before" run wasn't actually the failing case.
2. **Stage Phase 1 behind the default-OFF switch.** Confirm the OFF path is byte-for-byte unaffected (diff the boot log/RPT sequence against a same-day OFF-path boot).
3. **Cold boot #1 with the switch ON.** Capture the full evidence chain: the pre-bounce preseat line (may still show WEST/EAST — expected), log evidence the kill+relaunch actually fired for the mis-seated HC only, the post-bounce preseat line for the same HC name at the new RPT offset, **and, non-negotiable, a role-select roster screenshot taken after the bounce settles** confirming the HC now shows in the CIV/grey row and the BLUFOR/OPFOR occupied count no longer includes it. RPT alone is insufficient — it was RPT (`reseat=done|sideNow=CIV`) that produced the 2026-08-05 false read while the roster still showed BLUFOR; the roster is the check that actually catches this class of bug.
4. **Repeat 2 more times (3 cold boots total).** The underlying timing correlation is empirical, not proven (§2 contradictions #1–2); one clean run does not rule out a race.
5. **Affinity check:** after any bounce fires, confirm the new HC PID's CPU affinity matches the expected mask (reuse `Verify-4HC.ps1`'s own recompute logic), not the stale old-PID pinning.
6. **Bounded-retry / fail-closed check:** deliberately block one relaunch attempt and confirm the chain stops at the max-bounce ceiling, logs CRITICAL, and alerts rather than looping or silently reporting success.
7. **Human/GUER/JIP non-interference check:** with the switch ON, have a real human join BLUFOR and a real/test human join GUER during and immediately after a test cold boot; confirm normal enrollment speed, `HCLOBBY` still opens normally once both HCs register, and no GUER slot is ever touched by this mechanism.
8. **Automated corroboration (supplement, not substitute):** run `Tools/Smoke/Test-WaspBootSmoke.ps1` against the resulting RPT; `HCPRESEAT` should read PASS. This reads the same signal the bounce gate itself uses, so it corroborates internal consistency, not independent proof — the roster screenshot in step 3 remains the authoritative check.
9. **Phase 2 verification, independent of Phase 1:** within the pre-reseat window of a (possibly still-unpatched, for this specific test) mis-seat, force a commander vote and confirm the AI/abstain tally is no longer inflated by the stale HC magnet-group (2a); force/await a match-end stats flush during the same window and confirm no phantom stats-DB row or "has no score to be saved" warning references the HC (2b/2c).
10. **Sign-off gate:** present all before/after RPT excerpts + screenshots (all 3 cold boots) to the owner before flipping the Phase 1 switch to default-ON on the live box, and before considering the optional `RequireHcPreseat=true` follow-up (1e).

## 9. Rejected alternatives

1. **Raise `WFBE_C_HC_LOBBY_TIMEOUT` a fourth time.** Rejected — this lever gates player-holding on the *mission* side and has already been raised three times (90→150→240) without ever fixing engine-level seating (`Init_CommonConstants.sqf:3521-3522`, verified); it was never the actual root-cause lever (that lever is the box launcher's own `MATCH`-wait ceiling, a different mechanism entirely).
2. **Mission-ordered kick/disconnect of a mis-seated HC.** Rejected — proven inert on the live box today (`BattlEye=0`, `server-pr8.cfg:25`, verified this session); the one shipped kick primitive is BE-filter-mediated and BE was previously disabled specifically because it killed HC connections. Re-enabling BE-for-HCs is a separate, bigger, riskier lane the owner has not ordered here.
3. **Reorder mission.sqm so HC slots sit at the very end of id/declaration order.** Rejected — verified this session that an ordinary WEST slot (`id=9107`) already sits above the HC slots (`9009`/`9010`), which are already far above nearly all human slots, and the mis-seat still happens; slot position is not the driver, so reordering buys a cosmetic invariant while carrying live `sync[]`-reference regression risk for zero measured benefit.
4. **New mission-side telemetry FSM mirroring the box's bounce decision.** Rejected — the existing `HCSIDE|v1|preseat`/`reseat-result` telemetry already gives a box script everything it needs; a second, derived "dirty" signal is a second source of truth that can drift from the first for no added capability.
5. **"Accept-and-harden only," with no attempt at the engine-level fix, as the primary strategy.** Rejected as *primary* (retained as Phase 2, defense-in-depth) — the owner explicitly asked to fix HC seating "once and for all." Mission SQF genuinely cannot touch the engine-level slot binding, so the only lever that can actually free a mis-seated slot (a bounce) has to be attempted, not merely contained around, even though the containment fixes are individually sound and cheap enough to ship regardless.
6. **Treating `HCSIDE|v1|reseat|result=done|sideNow=CIV` alone as proof of correct seating.** Rejected — this is exactly the false-positive the 2026-08-05 evidence exposed (reseat reported done/CIV while the lobby roster still showed BLUFOR). Any verification step must read the pre-reseat `engineSide=` line and/or the human-visible role-select roster; never the post-reseat line alone.
